# agent_os4

نواة واحدة صغيرة، بديلة عن فوضى agent-os-v3 القديمة (300+ ملف، عدة
"عقول" متوازية). كل الكود هنا جديد ومختبر فعلياً سطراً بسطر — لا شي
مكتوب ولم يُجرَّب.

بناءً على طلبك، os4 الآن أساس "الشركة" اللي وصفتها (راجع قسم **خريطة
الهيكل الكامل** بالأسفل) — لكن كل اسم فيها مُطبَّق كشخصية تستخدم نفس
المخ والبوابة الموحّدين، لا كنظام منفصل بحالته وبنيته الخاصة. 40+ اسم،
مخ واحد، بوابة موافقة واحدة.

## البنية

| ملف | المسؤولية |
|---|---|
| `env.py` | تحميل `.env` مرة واحدة ومضمونة (يصلح بَق حقيقي كان بالنسخة القديمة) |
| `brain.py` | مخّ واحد: Claude أولاً، تراجع تلقائي لمزودين مجانيين لو فشل |
| `safety.py` | مصدر حقيقة واحد لأمان الأوامر والمسارات |
| `approval.py` | بوابة موافقة واحدة، مستويان فقط (تلقائي / يحتاج موافقة) — لا "متوسط" ولا مهلة تنتهي بتنفيذ صامت |
| `tools.py` | الأدوات الحقيقية: ملفات، أوامر، sandbox، + أدوات `pc_*` (وصول كامل حقيقي للجهاز، معطّلة افتراضياً) |
| `sandbox.py` | يد معزولة عبر Daytona (نسخة مُصلَحة من القديم) |
| `obsidian.py` | جسر لـ`obsidian_vault.py` الأصلي (مُختبر، يُستخدم كما هو) |
| `memory.py` | ذاكرة كلمات مفتاحية صادقة — بلا وعد "embeddings" غير موجود |
| `status.py` | لقطة حالة حقيقية (موافقات معلّقة، عدد الذكريات، تهيئة المفاتيح) — للعرض الخارجي فقط |
| `housekeeping.py` | يرتب الذاكرة بعد كل جلسة: يفضي `memory.json` ويؤرشفه بملاحظة Obsidian واحدة (بتلخيص لو فيه مخ، وبقائمة خام بصدق لو لا) |
| `self_improve.py` | تطوير ذاتي: اقتراح تعديل لملف داخل الحزمة — يُختبر بساندبوكس Daytona معزول، ولا يُطبَّق إلا بموافقة صريحة على الـdiff الكامل. لا استثناء لأي ملف. |
| `roles.py` | سجل الأدوار المسمّاة (Owner Authority + Global Expert Network + مجلس المراجعة) — بيانات فقط، كل دور شخصية فوق نفس `brain.ask()` |
| `decision.py` | منظومة الفصل بالقرارات: Decision Engine / Approval Authority / Rejection Authority / Appeals Board / Decision Evidence Ledger — طبقة توثيق فوق `approval.py`، ليست بوابة ثانية |
| `bots.py` | بوت واحد لكل مديرية من الثمانية — شخصية + أدوات محصورة، نفس `kernel.py`/`decision.py` |
| `chatroom.py` | غرفة نقاش جماعي بين البوتات — نص وعرض فقط، بلا أي مسار تنفيذ جديد |
| `skills.py` | سجل مهارات بنُسخ، مع حماية تراكمية من التراجع (Regression Testing) عبر كل تاريخ المهارة |
| `docs_sync.py` | تزامن التوثيق (مستوحى من مهارة neat-freak، مبسّط): يفحص تطابق التوثيق مع الكود الفعلي، يقترح تعديلات عبر `decision.py` بموافقة صريحة — لا تعديل تلقائي أبداً |
| `evidence.py` | تحقق مستقل من الادّعاءات (False Success Detector لـ`write_file`) + إحصاءات تدقيق حقيقية فوق `decision.ledger()` |
| `router.py` | التوجيه الذكي (Supreme Orchestrator الفعلي) — نص حر يُصنَّف تلقائياً لبوت مناسب أو مسار عام، بدل حفظ أوامر |
| `metrics.py` | لقطة أرقام حقيقية مجمّعة (قرارات، استخدام بوتات، ذاكرة، مهارات) — عدّ فقط، لا تقييم لغوي |
| `kernel.py` | الحلقة: خطة ← تنفيذ ← موافقة عند الحاجة ← **تحقق مستقل من الدليل** ← توقف عند أول فشل ← تقرير صادق. `interactive=False` + `resume_task()` تجعلها قابلة للإيقاف والاستئناف — لا تحجب أي خيط |
| `web_chat.py` | شات ويب حقيقي ("نسخ لصق") فوق نفس `router.py`/`kernel.py` — صفحة HTML + `/api/chat` + `/api/confirm`، + `/dashboard` لوحة تحكم حية + `/api/dashboard` + `/api/dashboard/decide` + `/api/dashboard/pc-toggle` (مقيّد بـlocalhost فقط) |
| `deploy.py` | ينشر `web_chat.py` داخل ساندبوكس Daytona معزول، يرجّع رابط معاينة موقَّع تفتحه بالمتصفح مباشرة |
| `rooms.py` | سجل رسائل لكل غرفة قسم على حدة (8 بوتات + غرفة تنفيذية)، + `recent_all()` لمراقبة كل الأقسام مجتمعة — تخزين وعرض فقط، التنفيذ عبر `kernel.py` بالضبط مثل أي مهمة |
| `cli.py` | `python -m agent_os4.cli` — `مساعدة` تعرض كل الأوامر الخاصة؛ النص الحر يُوجَّه تلقائياً؛ `انشر` ينشر الشات على Daytona |

## ما تم اختباره فعلياً هنا (بدون محاكاة)

- `safety.is_safe_command` / `validate_path` — يرفض الأوامر والمسارات الخطرة.
- `tools.write_file` / `read_file` / `run_command` — كتابة وقراءة حقيقية، حماية من الهروب خارج `data/workspace`.
- `approval.request` / `resolve` / `pending` — الطلب يبقى معلّق حتى موافقة صريحة.
- `obsidian.write_note` — يكتب ملاحظة Obsidian حقيقية (نفس الملف القديم، مُختبر مباشرة).
- `kernel.run_task` كامل end-to-end (بخطّة JSON محاكاة فقط لعدم وجود مفتاح API هنا؛ التنفيذ الفعلي للخطوات والموافقة والتقرير كله حقيقي).
- **ربط agency-site**: أضفت نقطة نهاية جديدة `/api/os4/status` في `web_bridge.py` الموجود (بدون لمس أي نقطة نهاية قديمة) تعرض لقطة حقيقية من `status.snapshot()`. شغّلت السيرفر حقيقةً وطلبت كل النقاط (`/api/os4/status` الجديدة + الثلاث القديمة) بـ`curl` وتأكدت إنها كلها ترجع 200 وبيانات صحيحة، قبل وبعد التعديل.
- **`housekeeping.tidy()`**: اختبرته حقيقةً 3 حالات — جلسة فاضية (صفر ذكريات → لا تُكتب ملاحظة)، جلسة فيها ذكريات بدون مخ متاح (الحالة الحقيقية بهذا الصندوق: يكتب القائمة الخام بصدق، `summarized: False`)، وتأكدت من محتوى ملف Obsidian الناتج فعلياً على القرص بمجلد `inbox/` (الصح تقنياً — نفس تصنيف `mirror_memory_item` القديم، `wiki` لمعرفة مستقرة فقط).

## التطوير الذاتي (`self_improve.py`) — أخطر جزء، اقرأ هذا

هذا الجزء الوحيد اللي يقدر يعدّل كود الوكيل نفسه — حتى `safety.py` و
`approval.py` (بوابتي الأمان نفسهما) غير مستثنيين، بناءً على طلبك
الصريح. الحماية مبنية على شرطين بلا استثناء ولا باب خلفي لأي ملف:

1. **اختبار إجباري بساندبوكس Daytona معزول** قبل أي شيء آخر — يرفع
   الحزمة كاملة (+ `obsidian_vault.py`) بالملف المقترَح معدَّلاً، يشغّل
   `py_compile` ثم يستورد كل ملفات الحزمة فعلياً هناك. **فشل الاختبار،
   أو حتى تعذّر الوصول لـDaytona نفسه، يوقف كل شيء فوراً — لا يصل أبداً
   لمرحلة طلب الموافقة.** هذا تحقّق منه حياً (أدناه)، وليس افتراضاً.
2. **موافقتك الصريحة على الـdiff الكامل** (الفرق الحقيقي سطراً بسطر،
   لا وصف عام) عبر نفس `approval.py` المستخدم لكل شيء آخر.
3. عند `apply()`: نسخة احتياطية من الملف القديم تُحفظ أولاً دائماً بـ
   `data/self_improve_backups/` قبل أي كتابة.

**ما تم اختباره فعلياً هنا:**
- بناء الحزمة المضغوطة (tarball) للاختبار — فككتها محلياً وتأكدت من
  محتواها صح (14 ملف + الملف المستهدف مُستبدَل بالمحتوى الجديد بالضبط).
- **المسار الآمن الأهم**: استدعيت `propose()` حقيقةً وDaytona فعلاً غير
  قابل للوصول من هذا الصندوق — تأكدت أن النتيجة `ok: False` عند مرحلة
  `sandbox_test`، وأن عدد طلبات الموافقة المعلّقة وعدد الاقتراحات
  المحفوظة بقيا صفر قبل وبعد. يعني: تعذّر الساندبوكس = رفض كامل، لا
  تجاوز صامت.
- `apply()`: زرعت طلب موافقة ومُوافَقاً عليه يدوياً على ملف تجريبي
  معزول (غير كود حقيقي)، تأكدت أن المحتوى تغيّر فعلياً على القرص، وأن
  النسخة الاحتياطية طابقت المحتوى القديم حرفياً، وأن الاقتراح حُذف بعد
  التطبيق. وتأكدت أن `apply()` على طلب **غير** موافَق عليه يرفض ولا
  يغيّر الملف إطلاقاً.
- حماية المسار (`_real_path`): رفضت `../env.py`، `../../etc/passwd`،
  `data/evil.py`، `sub/dir/x.py`، وأي امتداد غير `.py` — فقط ملفات
  مباشرة داخل `agent_os4/` مسموحة.

**ما يحتاج تجربتك على جهازك الحقيقي:** المسار الكامل end-to-end (من
`تحسين` إلى اختبار ساندبوكس حقيقي ناجح إلى موافقة إلى `طبّق`) غير
مُختبر هنا فعلياً — نفس قيد شبكة Daytona أدناه. لا تثق بأي شيء أعلاه
كـ"مُختبر بالكامل" قبل ما تجربه إنت على ملف حقيقي بسيط أولاً.

## ما يحتاج تجربتك على جهازك الحقيقي

- **Claude**: ضع `ANTHROPIC_API_KEY` بملف `.env` (لا تشاركه هنا).
- **Daytona sandbox**: المفتاح موجود، لكن بيئة التطوير هذي ما تقدر تتواصل مع `app.daytona.io` (سياسة شبكة). جرّبه إنت — هذا يشمل التطوير الذاتي كامل، لأنه يعتمد على الساندبوكس بالكامل.

## منظومة الأدوار والقرارات (`roles.py` + `decision.py`)

تطبيق حرفي للهيكل اللي أرسلته، بفلسفة واحدة: **40+ اسم، مخ واحد،
بوابة موافقة واحدة.** كل "Chief X Officer" أو "Engine/Authority" هو
سطر بيانات بـ`roles.py` (برومبت شخصية) يستدعي `brain.ask()` نفسه —
مو نظاماً مستقلاً بكوده وحالته وبَقّه الخاص. هذا تحديداً يمنع ما حذّرتك
منه: عشرات الأنظمة المتوازية المحتملة الأعطاب.

- **Owner Authority** = أنت حرفياً. `roles.py` يرفض صراحة أي محاولة
  لاستدعاء `brain.ask()` نيابة عنك (`human: True`، اختُبر حياً).
- **Global Expert Network / مجلس المراجعة المستقلة** = سجل أدوار سمّيتها
  بالضبط من رسالتك (Supreme Orchestrator, Chief Decision/Risk/
  Verification/Security/Ethics Officer, Independent Reviewer).
- **ADJUDICATION & DECISION SYSTEM** (أهم إضافة بهيكلك، بنص كلامك):
  - `decision.propose()` = **Decision Engine** — يفتح طلباً عبر
    `approval.py` نفسها (توثيق "من اقترح" إضافي، لا بوابة ثانية).
  - **مراجعة مستقلة تلقائية**: أي طلب يلمس ملفاً حساساً (`safety.py`،
    `approval.py`، `decision.py`، `roles.py`) يستدعي تلقائياً
    `roles.consult("independent_reviewer", ...)` ويُرفق رأيه بالطلب —
    دليل إضافي لك، لا بديل عن موافقتك.
  - `decision.approve()` / `decision.reject()` = **Approval Authority**
    / **Rejection Authority** — غلاف فوق `approval.resolve()`.
  - `decision.appeal()` = **Appeals & Reconsideration Board** — يرفض
    الاستئناف لو كان نفس سبب الرفض الأصلي حرفياً، يفتح طلباً جديداً
    مرتبطاً فقط لو فيه دليل جديد فعلي.
  - `decision.ledger()` = **Decision Evidence Ledger** + **Decision
    Review & Audit** — سجل زمني كامل: من اقترح، من قرر، رأي المراجعة.

**ما تم اختباره فعلياً هنا:**
- طلب عادي لا يلمس ملفاً حساساً → صفر مراجعة مستقلة (صح، ما يحتاجها).
- طلب يذكر `safety.py` → يحاول مراجعة مستقلة فعلاً؛ لا مخ متاح بهذا
  الصندوق فسجّل الفشل بصدق (`"تعذّرت المراجعة المستقلة: ..."`) بدل ما
  يتظاهر بمراجعة لم تحدث — ولم يمنع الطلب (المراجعة دليل إضافي، مو
  اختبار قاطع مثل ساندبوكس `self_improve.py`).
- `proposed_by`/`decided_by` يُحفظان صح على السجل الحقيقي بـ`approval.py`.
- `approve()`/`reject()` يسجّلان باللدجر بنجاح.
- **وجدت وأصلحت بَقاً حقيقياً أثناء الاختبار الحي**: فحص "هل الاستئناف
  فيه دليل جديد؟" كان يقارن مع نص الطلب الأصلي بدل سبب الرفض الفعلي
  (اللي `reject()` ما كان يحفظه أصلاً بمكان قابل للمقارنة) — فكان يقبل
  استئنافات بلا أي دليل جديد فعلياً. أصلحته: يقارن الآن مع آخر سبب رفض
  محفوظ باللدجر نفسه. اختبرت الحالتين بعد الإصلاح: استئناف بنفس سبب
  الرفض حرفياً يُرفض، واستئناف بدليل جديد فعلي يفتح طلباً مرتبطاً.
- فحص رجعي: تأكدت `self_improve.py` و`kernel.py` و`cli.py` لسا تشتغل
  صح بعد تعديل `approval.py` (إضافة `proposed_by`/`decided_by` بقيم
  افتراضية — لا كسر للتوقيع القديم).

## البوتات المساعدة (`bots.py`) — Mission Control

كل بوت = شخصية (persona) + أدوات محصورة + مديرية، يمر من نفس
`kernel.run_task()`/`decision.py`/`safety.py` الموجودين — لا بنية تحتية
منفصلة لكل بوت. تسجيل بوت جديد = سطر بيانات بـ`BOTS`، لا ملف جديد.

ثلاثة بوتات أولية (كل مديرية مُمثَّلة بقدر يسمح بالاختبار الحقيقي):
`research_bot` (بحث/تحليل، بلا أدوات تنفيذ إطلاقاً)، `docs_bot`
(توثيق، قراءة/كتابة ملفات فقط)، `ops_bot` (عمليات، ساندبوكس فقط — لا
لمس جهازك مباشرة).

`kernel.run_task()` تحوّل من `approval.py` مباشرة إلى `decision.py` —
فكل مهمة (من بوت أو منك مباشرة) تُسجَّل بـ`decision.ledger()` بمن
اقترحها، وتحصل تلقائياً على مراجعة مستقلة لو لمست ملفاً حساساً، تماماً
مثل `self_improve.py` (رُحِّل هو الآخر لنفس المسار).

**ما تم اختباره فعلياً هنا:**
- `research_bot` (بلا أدوات): خطة تحاول `write_file` تُرفض فوراً قبل أي
  تنفيذ — `"أداة غير مسموحة لهذا الدور"`؛ ومحادثة عادية بلا أدوات ترد
  مباشرة بلا رفض.
- `docs_bot`: `write_file` (مسموحة له) تمر لمرحلة موافقة حقيقية، وافقت
  عليها، والملف اتكتب فعلاً على القرص (تأكدت من محتواه)، والموافقة +
  الاقتراح اتسجّلا بـ`decision.ledger()` باسم `docs_bot`؛ أما
  `sandbox_bash` (غير مسموحة له) فرُفضت فوراً.
- اسم بوت غير موجود → خطأ واضح، لا فشل صامت.
- ملاحظة Obsidian الناتجة موسومة تلقائياً بـ`#اسم_البوت` (تحقّقت من
  المحتوى الفعلي على القرص) — تقدر تفلتر فعل كل بوت بذاكرتك مباشرة.
- **فحص رجعي بعد ترحيل `kernel.py`/`self_improve.py` من `approval.py`
  المباشر إلى `decision.py`**: مهمة عادية بدون بوت (`proposed_by`
  الافتراضي `"owner"`) لسا تشتغل وتُسجَّل صح؛ `self_improve.propose()`
  لسا يفشل بأمان (صفر طلبات موافقة) لما Daytona غير قابل للوصول، بالضبط
  كما قبل الترحيل.
- `cli.py`: اختبرت `_handle_list_bots`، `_handle_run_bot` (بوت موجود
  وغير موجود وصيغة ناقصة)، `_handle_ledger`، و`_handle_resolve` (يمر
  الآن عبر `decision.approve/reject` بدل `approval.resolve` المباشر)
  — كلها تُستدعى مباشرة وتُعطي النتيجة الصحيحة.

### توسيع البوتات للـ8 مديريات كاملة (مكتمل)

أضفت `intelligence_bot`، `financial_bot`، `security_bot`،
`customer_business_bot`، `learning_evolution_bot` — كل مديرية من
هيكلك عندها بوت واحد الآن (تأكدت برمجياً: `{b.directorate for b in
bots} == DIRECTORATES` بالضبط). أغلبها استشاري بحت (بلا أدوات تنفيذ) —
قرار متعمّد: ما فيه قدرة مالية أو تنفيذية حقيقية بالنظام حتى الآن، فلا
داعٍ تظاهر بصلاحيات وهمية لها.

زي [ChatDev](https://metaschool.so/ai-agents/chatdev) — فكرة موحّدة:
غرفة واحدة، بوتات "موظفين" يتناقشون بصوت عالٍ، كل الكلام مرئي ومسجّل،
وأي أثر فعلي حقيقي يحتاج موافقتك. بنيتها بنفس الفلسفة:

- `chatroom.discuss(bot_keys, topic, rounds)` — كل بوت بالترتيب يشوف
  المحادثة كاملة (بما فيها رد البوت اللي قبله بنفس الجولة) قبل يرد
  بشخصيته — نقاش متراكم حقيقي، لا ردود متوازية تتجاهل بعضها.
  `chatroom.history()` — يعرض كامل السجل.
- **لا يفتح مسار تنفيذ جديد عمداً**: الغرفة للنقاش والعرض فقط. أي قرار
  يخرج من نقاش يحتاج يمر عبر `bots.run()` العادية (أدواتها محصورة،
  موافقتك مطلوبة) — بالضبط زي أي مهمة ثانية، بلا اختصار.

**ما تم اختباره فعلياً هنا:**
- نقاش حقيقي بين بوتين: تأكدت (بفحص نص البرومبت الفعلي المُرسَل لكل
  بوت، لا افتراضاً) أن البوت الثاني يستقبل رد البوت الأول ضمن سياقه قبل
  ما يرد، وأن كل بوت يرد فعلاً بمحتوى مختلف مطابق لشخصيته (لا رد موحّد
  أو مكرر).
- التاريخ محفوظ على القرص بالترتيب الصحيح (owner يفتح الموضوع، ثم كل
  بوت بدوره).
- بوت غير موجود بقائمة النقاش → يُرفض بخطأ واضح **قبل** أي كتابة جزئية
  بالغرفة (لا حالة نصف-مكتوبة).
- **الحالة الحقيقية بدون مفتاح مخ** (هذا الصندوق): كل بوت يفشل بصدق
  برسالة واضحة باسمه (`"تعذّر رد research_bot: ..."`) تُسجَّل بالغرفة
  كما هي — فشل بوت واحد ما يوقف نقاش بقية البوتات، وما فيه أي رد مزيّف.
- `cli._handle_discuss`/`_handle_room` (أوامر `نقاش`/`الغرفة`) مُختبرة
  مباشرة بنفس الحالات.

## Conflict/Deadlock Resolution (`chatroom.resolve`)

- `chatroom.resolve(bot_keys, topic, rounds)` تدير نقاشاً ثم تجمع
  توصية نهائية صريحة من كل بوت (نص مباشر، لا تخمين دلالي من مخ ثانٍ).
  توصيات متطابقة حرفياً = توافق = **طلب موافقة واحد**. توصيات مختلفة =
  تعارض حقيقي = **طلب موافقة منفصل لكل توصية**، كل واحد يذكر مؤيديه
  والتعارض مع البقية — أنت تختار، لا حسم آلي لخلاف حقيقي أبداً.
  Deadlock Resolution مدمج: النقاش محدود بـ`rounds` (لا جدل بلا نهاية)،
  وأي خلاف يُحال لك صراحة بدل ما يبقى معلّقاً أو يُحسم عشوائياً.

**ما تم اختباره فعلياً هنا:**
- توافق حقيقي (كل البوتات نفس التوصية) → طلب موافقة واحد بالضبط.
- تعارض حقيقي (توصيات مختلفة) → طلبا موافقة منفصلان، كل واحد يذكر
  التعارض بوضوح، صاحب النظام يختار.
- **بَق حقيقي وجدته بالاختبار الحي وأصلحته**: أول نسخة كانت تعامل فشل
  كل البوتات (بدون مفتاح مخ) كـ"توافق بالإجماع" وتفتح طلب موافقة على
  فراغ — لأن كل البوتات فشلت بنفس نص الخطأ حرفياً فتطابقت "توصياتها"!
  أصلحته: الفشل يُستبعد من المقارنة تماماً، فشل الكل = `outcome:
  "failed"` بلا أي طلب موافقة، فشل البعض يُذكر صراحة مع توافق/تعارض من
  بقي. اختبرت الحالات الثلاث (فشل كامل، فشل جزئي، نجاح كامل) بعد الإصلاح.
- `cli._handle_resolve_discussion` (أمر `احسم`) مُختبر بنفس الحالات.

## طبقة التعلّم والتطور (`skills.py` + `self_improve.restore`)

- **Skill Registry & Version Control**: `skills.register(name, prompt_template, examples)`
  يسجّل نسخة مُرقَّمة من مهارة. `skills.use(name, input)` يستخدم آخر
  نسخة معتمدة.
- **Regression Testing Authority**: قبل اعتماد أي نسخة جديدة، تُعاد
  تجربة **كل** أمثلة **كل** النسخ السابقة (متراكمة، لا آخر نسخة فقط)
  على القالب الجديد — فشل أي مثال قديم واحد يرفض النسخة الجديدة كاملة.
- **Rollback & Recovery Authority**: `self_improve.restore(filename)`
  — يقترح الرجوع لآخر نسخة احتياطية (أو نسخة محددة)، عبر نفس
  `decision.py`/موافقتك/`apply()` الموجودين بالضبط — بلا استثناء "آمن"
  لأنه رجوع، نفس القاعدة بلا تمييز.
- **Sandboxed Experimentation + Self-Evolution Governance**: موجودتان
  فعلياً — نفس `self_improve.py` بساندبوكسه الإجباري.
- **Model Evaluation & Routing**: موجود فعلياً بـ`brain.py` (تراجع
  تلقائي Claude ← Ollama ← Gemini ← Groq)؛ لم أضف قياس أداء/تكلفة فعلي
  لأنه يحتاج مفاتيح حقيقية لأكثر من مزود لأقيسه بصدق، لا افتراضاً.

**ما تم اختباره فعلياً هنا:**
- تسجيل نسخة 1 ناجحة، نسخة 2 تمر بكل أمثلة 1، نسخة 3 **تكسر مثالاً من
  النسخة 1 تحديداً** (رغم نجاحها بأمثلة النسخة 2) → اكتُشفت ورُفضت
  كاملة. هذا بالذات كان بَقاً حقيقياً وجدته بالاختبار الحي: أول نسخة من
  الكود كانت تقارن مع آخر نسخة فقط، فمثال النسخة 1 كان يفقد حمايته بعد
  نسخة واحدة لاحقة. أصلحته ليتراكم عبر كل التاريخ، واختبرت الإصلاح.
- `use()` يستخدم فعلاً آخر نسخة **معتمدة** (لا المرفوضة).
- `self_improve.restore()`: زرعت نسخة احتياطية حقيقية، استرجعتها —
  بقيت معلّقة لحد الموافقة الصريحة (لم تُطبَّق تلقائياً)، وبعد الموافقة
  `apply()` (الموجودة أصلاً، بلا مسار تنفيذ جديد) طبّقتها فعلاً على
  القرص وتأكدت من المحتوى — وبالمناسبة أخذت نسخة احتياطية من الحالة
  "الحالية" تلقائياً، فحتى الاسترجاع قابل للتراجع عنه هو الآخر.

## طبقة الأدلة والجودة (`evidence.py`)

- **Claim Verification + False Success Detector**: `evidence.verify_write()`
  — بعد أي `write_file` ناجح ظاهرياً، `kernel.py` يعيد قراءة الملف من
  القرص مباشرة ويقارنه حرفياً بالمحتوى المُدّعى كتابته، بدل تصديق
  `"ok": True` من الأداة نفسها بلا تحقق ثانٍ.
- **Decision Review & Audit**: `evidence.audit()` — إحصاءات حقيقية
  (كم اقتُرح، كم وافق، كم رُفض، نسبة الموافقة، لكل جهة) محسوبة مباشرة
  من `decision.ledger()` — عدّ فعلي، لا تقييم لغوي من مخ قابل للتحيّز.

**ما تم اختباره فعلياً هنا:**
- `verify_write()`: ملف مطابق → `verified: True`؛ ملف محتواه مختلف
  فعلياً → `verified: False` بسبب واضح؛ ملف غير موجود أصلاً رغم الادّعاء
  → `verified: False` بسبب واضح.
- **الاختبار الأهم**: محاكيت أداة تكذب (`tools.run` مُموَّهة ترجّع
  `"ok": True` بينما الملف الفعلي على القرص مختلف عن المُدّعى) — التحقق
  المستقل داخل `kernel.py` اكتشف الكذبة فعلياً وقلب النتيجة لفشل،
  والحكم النهائي صار "جزئي" لا "تمام". هذا تحديداً هو False Success
  Detector يعمل، لا مجرد وجود الكود.
- `evidence.audit()` على بيانات حقيقية متراكمة من الاختبارات، أرقامه
  طابقت العدّ اليدوي.
- فحص رجعي شامل: `bots.run()` و`self_improve.propose()` لسا يشتغلان
  صح بعد دمج `evidence.py` بـ`kernel.py`.

## التوجيه الذكي (`router.py`) — ما تحتاج تحفظ أوامر

قبل هذا، لازم تكتب "بوت docs_bot اكتب..." حرفياً. الآن تكتب طلبك
عادي وهذا يقرر الوجهة: لو الطلب يطابق تخصص بوت معيّن بوضوح يتولاه هو
تلقائياً (بأدواته المحصورة وبوابة موافقته كالمعتاد)، وإلا مسار عام —
بالضبط زي ما أسوي أنا. هذا أول استخدام فعلي حقيقي لشخصية
`supreme_orchestrator` المسجّلة بـ`roles.py` (كانت موثّقة بس بلا وظيفة).

التصنيف نفسه بلا أي أثر جانبي — غلطة تصنيف أسوأ حالة ترسل الطلب
للمسار العام (نفس السلوك القديم). لا يغيّر أي بوابة أمان: البوت
المختار لسا محصور بأدواته، والموافقة لسا مطلوبة بالضبط كالمعتاد.

**ما تم اختباره فعلياً هنا:**
- تصنيف يختار بوتاً محدداً بوضوح، تصنيف عام صريح، ورد بوت وهمي من
  المخ (يُرفض ويرجع للعام — فشل آمن)، ورد بلا JSON إطلاقاً (نفس الشي)،
  وبدون مفتاح مخ حقيقي (الحالة الفعلية هنا — نفس الشي، فشل آمن للعام).
- **مسار كامل end-to-end**: نص حر دخل بدون أي أمر خاص → صُنِّف تلقائياً
  لـ`docs_bot` → نُفِّذ فعلياً بأدواته المحصورة وبوابة موافقته → تحقق
  مستقل من الملف الناتج على القرص.

## طبقة التنفيذ والأدوات — توسيع (`tools.py`)

أداتان جديدتان، بنفس بوابة `safety.py`/الموافقة الموجودة، لا نظام منفصل:

- **`list_workspace()`** (Universal Tool Gateway/File Intelligence) —
  قراءة فقط، تلقائية (بلا موافقة)، تسرد ملفات مساحة العمل.
- **`browser_screenshot(url, filename)`** (Browser & Computer Control)
  — لقطة شاشة فقط، **بدون أي نقر أو كتابة أو تفاعل** عمداً، لتقليل
  سطح الهجوم (لا إدخال بيانات اعتماد، لا تنفيذ تفاعلي). يخرج للإنترنت
  → يحتاج موافقة. يرفض أي رابط غير `http(s)://` صراحة (يمنع حتى
  `file://` لمنع كشف ملفات محلية عبر الأداة).

**قرار متعمّد لم أبنِه: Secrets & Credential Vault.** `.env` نفسه هو
الخزنة الصحيحة فعلياً — لا تُقرأ قيمه أبداً عبر أي أداة يستدعيها
البوت، فقط `os.environ.get()` داخل `brain.py`/`sandbox.py` وقت
الاستخدام. بناء "خزنة" جديدة قابلة للقراءة عبر أداة يزيد سطح الهجوم،
لا ينقصه — تراجع أمني لا تحسين.

**ما تم اختباره فعلياً هنا:**
- `list_workspace()`: سرد ملفات حقيقية بمجلدات فرعية، صح ومطابق تماماً.
- `browser_screenshot()`: اختبرت آلية التصفح والتصيير والتقاط اللقطة
  فعلياً (صفحة محلية حقيقية) — أنتجت PNG صالح حقيقي على القرص (تحقق
  من الهيدر المغنطيسي `\x89PNG` وحجم الملف). **قيدان بيئيان صادقان،
  لا بَقّان بالكود**: (1) متصفح Chromium المُثبَّت مسبقاً بهذا الصندوق
  إصداره لا يطابق حزمة playwright المثبَّتة — الدالة المشحونة تعطي
  رسالة خطأ واضحة توجّه لتشغيل `playwright install chromium` بدل فشل
  غامض؛ (2) سياسة الشبكة هنا تمنع الوصول لنطاقات خارجية عشوائية (نفس
  قيد Daytona) — اختبرت هذا الجزء بمتصفح+صفحة حقيقيين محلياً لعزل
  "هل الآلية صحيحة" عن "هل الشبكة مفتوحة". رفض `browser_screenshot`
  لروابط غير صالحة و`file://` وهروب مسار — كلها مُختبرة.
- فحص رجعي عبر `kernel.py`: `list_workspace` ينفَّذ تلقائياً بلا
  موافقة، `browser_screenshot` يطلب موافقة فعلاً (تحقّقت من استدعاء
  `input()`) ثم يفشل بصدق بسبب قيد الشبكة — لا نجاح مزيّف.

## مؤشرات القياس (`metrics.py`)

`metrics.snapshot()` — لقطة أرقام حقيقية: القرارات (مُقترح/موافَق/
مرفوض/نسبة الموافقة)، استخدام كل بوت، عدد عناصر الذاكرة، عدد المهارات
المسجّلة. كلها عدّ فعلي فوق `evidence.audit()`/`memory.py`/`skills.py`
الموجودين — لا بنية تخزين جديدة. اختبرته ببيانات حقيقية مبنية يدوياً
وتأكدت الأرقام طابقت المدخلات تماماً.

## الشات عبر Daytona (`web_chat.py` + `deploy.py`) — "نسخ لصق" حقيقي

هذا كان طلبك الأصلي من أول يوم ("نسوي له شات نسخ لصق... اتوقع برنامج
Daytona") — ما كنت بنيته، بنيته الآن. `python3 -m agent_os4.cli` يبقى
موجوداً لمن يبي طرفية، لكن `انشر` يعطيك رابطاً تفتحه بالمتصفح وتكتب،
بدون أي تثبيت أو سطر أوامر على جهازك.

**التحدي الحقيقي اللي حليته**: شات بالطرفية يقدر يحجب على `input()`
لحد ما توافق. سيرفر HTTP ما يقدر — خيط الطلب يتعلّق للأبد ولا يرد أبداً
(هذا بالضبط كان بَق موثّق بتعليق بملف الشات القديم `agent_os/chat_api.py`
المرتبط بـjarvis_v2 المحذوف). الحل: **`kernel.py` صار قابلاً للإيقاف
والاستئناف فعلياً** — `interactive=False` يوقف عند أي خطوة تحتاج
موافقة، يحفظ مكانه بالضبط (المهمة، الخطوات، أي نتائج سابقة بنفس الخطة)
بدل ما يحجب، ويرجع فوراً. `kernel.resume_task(request_id)` يكمل من
نفس النقطة بالضبط بعد ما تُحسم الموافقة — لا يعيد الخطة من الصفر ولا
يكرر خطوة نُفِّذت فعلاً. هذا حلّ فعلياً فجوة "Durable Workflow Engine"
اللي كانت مؤجَّلة بخريطة الهيكل تحت — احتجناها فعلاً للشات، ما بنيتها
تخميناً.

**كيف يُنشر**: `deploy.py` يرفع حزمة `agent_os4` كاملة (نفس آلية
`sandbox.build_package_tarball_b64` المُختبرة أصلاً بـ`self_improve.py`،
نقلتها لـ`sandbox.py` لتُستخدم بالمكانين بلا تكرار منطق) لساندبوكس
Daytona جديد، يشغّل `web_chat.py` هناك بالخلفية، ويطلب رابط معاينة
**موقَّع** (`sandbox.create_signed_preview_url`) — يفتح مباشرة بالمتصفح
بلا أي ترويسة خاصة. **تفصيل مهم اكتشفته من قراءة مكتبة Daytona نفسها**:
هذا الرابط افتراضياً صالح **60 ثانية فقط** لو ما حدّدت مدة صراحة — لو
فاتني هذا كان أعطيتك رابطاً ميتاً خلال دقيقة. حدّدته صراحة (ساعة
افتراضياً، قابل للتغيير).

مفاتيحك تُمرَّر للساندبوكس عبر `env_vars` بباراميتر Daytona SDK نفسه
عند الإنشاء (حقل مخصص لهذا بالضبط) — لا تُضمَّن بنص سكربت، ولا أراها
أنا بأي لحظة؛ `deploy.py` يقرأها من `.env` المحلي على جهازك مباشرة.

**ما تم اختباره فعلياً هنا:**
- **الإيقاف/الاستئناف بالكامل، end-to-end**: خطة بخطوتين (الأولى
  تلقائية، الثانية تحتاج موافقة) بوضع `interactive=False` — توقفت
  بالضبط عند الخطوة الثانية، الأولى كانت منفَّذة وموجودة بالنتائج،
  `pending_request_id` صحيح. وافقت → `resume_task()` أكمل من نفس
  النقطة، كتب الملف فعلياً على القرص (تحققت من المحتوى)، أنهى بحكم
  "تمام". رفضت (بمحاولة مستقلة) → أنهى بحكم "جزئي" بلا أي تنفيذ.
  استئناف قبل الحسم → خطأ واضح. استئناف **مكرر** لنفس الطلب بعد
  استهلاكه → خطأ واضح، لا تنفيذ مزدوج. الحالة المعلّقة تُنظَّف من
  التخزين بعد كل استخدام — تحققت فعلياً.
- **فحص رجعي كامل**: المسار التفاعلي القديم (`interactive=True`
  الافتراضي، يستخدمه `cli.py`) اختبرته بعد كل إعادة الهيكلة — مطابق
  تماماً للسلوك قبلها، موافقة ورفض وبوتات كلها.
- **`web_chat.py` end-to-end حقيقي**: شغّلت السيرفر فعلياً (لا محاكاة)،
  `curl` حقيقي لـ`GET /` (200، العنوان صح) ولـ`POST /api/chat` — رجع
  خطأ صادق واضح لعدم وجود مفتاح مخ هنا، لا رد مزيّف. اختبرت الدوال
  مباشرة أيضاً: محادثة عادية، توجيه لبوت + طلب تأكيد، موافقة تُكمل
  وتكتب ملفاً حقيقياً على القرص، رفض ينهي بلا تنفيذ، طلب غير موجود
  يُرفض بوضوح.
- **`deploy.py`**: بلا `ANTHROPIC_API_KEY` → يرفض فوراً بمرحلة
  `preflight`، **قبل أي محاولة شبكة إطلاقاً** (لا تنشر شاتاً بلا مخ

الحاجة الفعلية). كل البيانات حقيقية من نفس الوحدات الموجودة فعلياً —
لا بنية تخزين جديدة:
- **حالة النظام**: `status.snapshot()` (مفتاح Claude، Daytona، وضع
  الوصول الكامل للجهاز) + عدد الطلبات المعلّقة + سجلات الذاكرة.
- **مؤشرات**: `metrics.snapshot()` (القرارات، استخدام كل بوت، المهارات).
- **طلبات معلّقة بانتظار موافقتك**: `approval.pending()` بالكامل، بزر
  "وافق"/"رفض" لكل طلب — يستدعي `/api/dashboard/decide`.
- **البوتات**: `bots.list_bots()`.
- **آخر القرارات**: `decision.ledger()` (موسّعة بحقل `what` حتى لِـ
  مرحلتي `approved`/`rejected` — يُعاد بناؤه من مرحلة `proposed`
  المطابقة بنفس `request_id` لو غاب، عرضاً فقط، بلا تعديل للسجل
  الفعلي، أحدث 20 الأحدث أولاً).

**التصميم** (طلبتها صراحة "تصميم جنوني احترافي" بعد ما أرسلت صوراً
مرجعية لعدة لوحات تحكم): واجهة داكنة باحترافية (sidebar أيقونات،
بطاقات KPI بتوهّج حسب الحالة، مقياس دائري لمعدّل الموافقة، رسم شبكة
SVG حي للبوتات الثمانية حول نواة `kernel.py` بخطوط متحركة ملوّنة حسب
المديرية وحجم/توهّج العقدة حسب الاستخدام الفعلي، سجل قرارات بشكل
طرفية (terminal) ملوّن حسب المرحلة، بحث حي يُصفّي البوتات والسجل).
**كل رقم ورسم مربوط ببيانات حقيقية من `_dashboard_data()` — صفر أرقام
مزخرفة أو حشو بصري بلا معنى**؛ لو فيه صفر طلبات أو صفر مهارات، تُعرض
كـ0 فعلي، لا تُخفى ولا تُلفَّق. بلا أي مكتبة خارجية (لا Chart.js ولا
أيقونات CDN) — SVG يدوي وCSS خالص، نفس فلسفة عدم إضافة اعتماديات
خارجية لسيرفر لازم يشتغل داخل Daytona/Fly.io/جهاز محلي بلا إنترنت
مضمون.

**تفصيل أمانة مهم بزر الموافقة**: `decision.propose()` يُستدعى من أكثر
من مكان — من حلقة `kernel.run_task()` نفسها (شات/بوت)، لكن أيضاً من
`docs_sync.py`/`self_improve.py`/`chatroom.py` مباشرة، بلا حالة
`kernel` معلّقة مرتبطة بها. فـ`/api/dashboard/decide`:
1. يسجّل القرار دائماً عبر `decision.approve/reject` (نفس بوابة
   الموافقة الوحيدة، لا بوابة ثانية).
2. لو الطلب من مسار `kernel` (موجود بـ`kernel.pending_tasks()`) —
   يكمل التنفيذ الفعلي فوراً عبر `resume_task()`، نفس زر "نفّذ" بالشات.
3. لو من مسار آخر (مثل `docs_sync.propose_doc_fix`) — يسجّل الموافقة
   فقط ويقول بوضوح إنها تحتاج أمرها الخاص للتطبيق (مثل `طبّق_توثيق`)
   — **لا يدّعي تطبيقاً لم يحصل فعلياً**.

**ما تم اختباره فعلياً هنا:** سيرفر HTTP حقيقي + طلبات حقيقية (لا
محاكاة): `GET /` و`GET /dashboard` يرجعان 200 وفيهما رابط متبادل
بينهما. `GET /api/dashboard` يرجع بيانات مطابقة فعلياً لما تولّده
`approval.py`/`decision.py`/`metrics.py` (تحققت: 8 بوتات، صفر طلبات
معلّقة قبل أي اختبار). أنشأت طلباً معلّقاً حقيقياً عبر `kernel.run_task`
وتأكدت ظهوره فوراً بالـAPI. وافقت عليه عبر `/api/dashboard/decide` —
تأكدت أن الملف كُتب فعلياً على القرص بالمحتوى الصحيح (قراءة مستقلة من
القرص، لا تصديق لرد الـAPI). اختبرت طلباً من مسار غير-`kernel`
(`decision.propose` مباشرة) — تأكدت أن الرد يقول بوضوح إن التطبيق
يحتاج أمراً منفصلاً، بلا ادّعاء كاذب. طلب غير موجود → رفض واضح. فوق
هذا، فتحت الصفحة فعلياً بمتصفح Chromium حقيقي عبر Playwright ببيانات
حقيقية مزروعة (طلبان معلّقان من نوعين مختلفين)، أخذت screenshot
وراجعته بصرياً — العرض صحيح ومقروء بالعربي RTL، الأزرار بمكانها.

**بعد إعادة التصميم الكامل**: زرعت بيانات أغنى وأكثر واقعية (3 بوتات

## الوصول الكامل للجهاز (`pc_*` بـ`tools.py`) — "نفس OpenCode"

طلبتها صراحة: "ابيه acces للبي سي كامل نفس opencode يوم يسوي أشياء
بجهازي". أربع أدوات جديدة: `pc_read_file`، `pc_write_file`،
`pc_list_dir`، `pc_run_command` — تعمل على **الجهاز الحقيقي** اللي
يشتغل عليه `agent_os4`، بلا حصر بمجلد `data/workspace`، نفس فلسفة
OpenCode/Claude Code: يعمل حيث استُدعي، لا بصندوق منفصل.

**معطّلة افتراضياً — قرار تصميم ثابت، لا استثناء:**
- `OS4_ALLOW_PC_ACCESS=1` بملف `.env` يفعّلها — غيابه يرجع خطأ عربي
  واضح من كل أداة PC، لا فشلاً صامتاً.
- `OS4_PC_ROOT` (اختياري) يحدد الجذر الافتراضي للمسارات النسبية —
  افتراضياً المجلد اللي شُغِّل منه `agent_os4` (`os.getcwd()`)، تماماً
  مثل OpenCode.
- كل الأربع أدوات **تحتاج موافقتك الصريحة** عبر `kernel.NEEDS_APPROVAL`
  — حتى `pc_read_file` (القراءة)، لأنها تكشف محتوى ملفات حقيقية حساسة
  محتملة على جهازك، بعكس `read_file` المحصورة بـ`data/workspace`.
  برومبت الخطة نفسه لا يذكر أدوات PC أصلاً إلا لو كانت مفعّلة
  (`kernel._plan_prompt()`) — المخ ما يعرف هذي الأدوات توجد لو معطّلة.

**الحماية الحقيقية هي موافقتك على نص كل أمر/مسار قبل أي تنفيذ، لا قائمة
بيضاء ضيقة تمنع أعمالاً شرعية**. فوقها، طبقة حماية إضافية من كوارث
معروفة لا رجعة فيها حتى لو وافقت بالخطأ (`safety.PC_FORBIDDEN_PATTERNS`):
`rm -rf /`، `format`، `mkfs`، `dd if=`، `shutdown`، `reboot`،
`diskpart`، وغيرها. ملفات `.env` محظورة كتابة/قراءة حتى بوضع PC.

**ملاحظة أمانة مهمة لم تُسأل عنها صراحة لكن يلزم ذكرها:** هذي الميزة
مفيدة فقط لما يشتغل `agent_os4` **مباشرة على جهازك** (`python -m
agent_os4.cli` أو `web_chat.py` محلياً). لو شغّلته عبر رابط Daytona
المؤقت أو الاستضافة الدائمة على Fly.io، فـ`pc_*` تشتغل على **تلك
الحاوية البعيدة**، لا على جهازك الحقيقي — لا فائدة فعلية لتفعيلها
بالمسارين المستضافين. `deploy.py` حالياً لا يمرّر `OS4_ALLOW_PC_ACCESS`
للساندبوكس عمداً — تفعيلها بالاستضافة البعيدة يعطي انطباعاً خاطئاً
بالغرض منها.

**ما تم اختباره فعلياً هنا (11 اختباراً، بلا محاكاة):**
- معطّلة افتراضياً: كل الأربع أدوات ترفض بوضوح، `kernel._plan_prompt()`
  لا يذكرها.
- تفعيل عبر `OS4_ALLOW_PC_ACCESS=1` — `safety.pc_access_enabled()`
  يتحول صح، البرومبت يذكر الأدوات.
- كتابة فعلية (`pc_write_file`) ثم قراءة مستقلة من القرص (لا تصديق
  لادّعاء الأداة) تطابقت تماماً.
- `pc_list_dir` حقيقي يعرض محتوى مجلد فعلي.
- `pc_run_command` حقيقي (`echo` + `ls`) نفّذ فعلاً عبر shell ورجع
  مخرجات حقيقية.
- كل أنماط `PC_FORBIDDEN_PATTERNS` (`rm -rf /`، `shutdown`، `mkfs`،
  ...) مرفوضة فعلياً حتى بوضع PC مفعّل.
- أمر عادي (`git status`, أمر عشوائي غير مدمّر) يُسمح بمراجعته — تأكدت
  عملياً إنها قائمة حظر لا قائمة بيضاء.
- `.env` محمي كتابة حتى بوضع PC.
- مسار مطلق خارج `PC_ROOT` يعمل فعلاً — لا حصر بمجلد واحد.
- `kernel.NEEDS_APPROVAL` يشمل الأربع أدوات فعلياً.
- `tools.REGISTRY` موصول صح للأربعة عبر نفس `tools.run()`.

**تدفق الموافقة الكامل عبر `kernel` مُختبر من طرف لطرف (برومت مخ
محاكى فقط، كل الباقي حقيقي 100%):** خطة بخطوة `pc_write_file` واحدة
عبر `run_task(interactive=False)` — توقفت عند بوابة الموافقة فعلاً،
الملف **لم يُكتب** قبل القرار (تحققت من القرص). محاولة `resume_task`
قبل أي قرار → رفض واضح. رفض الطلب → `resume_task` أنهى بدون كتابة أي
شيء أبداً (تحققت من القرص). طلب جديد مطابق → موافقة صريحة →
`resume_task` → **كُتب فعلياً على القرص** بالمحتوى الصحيح، الحكم
النهائي "تمام".

**ما يحتاج تجربتك على جهازك الحقيقي:** كل الاختبار أعلاه صار بصندوق
هذه الجلسة على مسارات `/tmp` مؤقتة — لم أختبر `pc_*` على جهازك
الحقيقي فعلياً (لا أملك وصولاً له). شغّل `python -m agent_os4.cli`
محلياً، ضع `OS4_ALLOW_PC_ACCESS=1` بملف `.env`، وجرّب طلباً بسيطاً
("اعرض محتوى مجلد كذا بجهازي") لترى موافقة حقيقية تطلب مراجعتك قبل أي
تنفيذ.

### تفعيلها من اللوحة نفسها (`/api/dashboard/pc-toggle`)

طلبتها صراحة: "تفعيل الوصول الكامل للجهاز من اللوحة نفسها" (بدل تعديل
`.env` يدوياً). مفتاح تبديل حقيقي ببطاقة KPI باللوحة — **بشرط واحد لا
استثناء له**: الطلب لازم يجي من **نفس الجهاز حرفياً** (`127.0.0.1`
أو `::1`، تحقق فعلي من `self.client_address` بكل طلب HTTP، لا مجرد
تلميح بالواجهة). السبب: اللوحة ممكن تكون مفتوحة عبر رابط Daytona/
Fly.io مستضاف على الإنترنت — لولا هذا الشرط، أي زائر يملك الرابط كان
يقدر يفعّل وصولاً حقيقياً كاملاً لجهاز المضيف عن بعد بضغطة واحدة. هذا
الشرط هو الحاجز الفعلي، مو ديكور بالواجهة فقط.

عند التفعيل من نفس الجهاز: يحدّث `os.environ` فوراً (ينعكس بنفس
اللحظة بلا إعادة تشغيل)، **ويحفظه فعلياً بملف `.env` على القرص**
(`dotenv.set_key` — قراءة وتعديل سطر واحد فقط، لا الكتابة فوق باقي
المفاتيح الموجودة)، ويُسجَّل بسجل القرارات (`decision.propose` +
`decision.approve`) عشان يظهر بسجل اللوحة الحي مثل أي قرار ثاني — تتبّع
كامل، لا تغيير صامت.

**ما تم اختباره فعلياً هنا (7 اختبارات، سيرفر HTTP حقيقي):**
- طلب من عنوان شبكة حقيقي غير-loopback لهذا الصندوق (ليس محاكاة) →
  رُفض بوضوح، ووضع PC **ما تفعّل فعلياً** (تحققت من `safety.pc_access_enabled()`
  بعد محاولة الرفض).
- طلب من `127.0.0.1` → نجح، `safety.pc_access_enabled()` صار `True`
  **بنفس العملية الجارية فوراً** بلا أي إعادة تشغيل.
- قراءة مستقلة لملف `.env` **من القرص نفسه** بعد التفعيل — احتوى
  فعلاً `OS4_ALLOW_PC_ACCESS=1`، وباقي المفاتيح الموجودة (`DAYTONA_API_KEY`)
  ما انمسحت.
- القرار ظهر فعلاً بـ`decision.ledger()` بنص واضح ("تفعيل وضع الوصول
  الكامل للجهاز").
- التعطيل من نفس الجهاز اشتغل بنفس الموثوقية — انعكس فوراً بالذاكرة
  وانحفظ بالقرص (`OS4_ALLOW_PC_ACCESS=0`).

## غرف الأقسام (`rooms.py` + `/rooms`) — شات لكل مديرية + مراقبة حية

طلبتها صراحة: "كل قسم له شات... ابي كاني اراقب محادثاتهم". تسع غرف
منفصلة — غرفة لكل بوت من بوتات `bots.py` الثمانية (نفس هيكل المديريات
الموجود، بلا تكرار بيانات) + غرفة "الإدارة العليا — مكتب صاحب النظام"
تنفيذية واحدة. كل غرفة خيط محادثة مستقل تماماً، وغرفة عاشرة خاصة
"مراقبة — كل الأقسام" (بالواجهة فقط، ليست غرفة حقيقية بالتخزين) تعرض
رسائل كل الغرف مجتمعة بترتيبها الزمني الحقيقي — هذا بالضبط معنى
"أراقب محادثاتهم".

**كيف تشتغل كل غرفة**: `rooms.py` نفسه لا يقرر ولا ينفّذ شيئاً — فقط
يخزّن ويعرض (نفس فلسفة `chatroom.py` بالضبط). التنفيذ الفعلي يمر حصراً
عبر `kernel.run_task()` العادي:
- غرفة بوت (مثل `docs_bot`) → `persona`/`allowed_tools` نفس البوت
  بالضبط من `bots.BOTS`، `proposed_by` باسم البوت — لا مسار تنفيذ
  مختلف عن `bots.run()` العادي، فقط واجهة شات مخصّصة له.
- غرفة `executive` → نفس مسار الشات العام (`proposed_by="owner"`،
  بلا شخصية ولا حصر أدوات) — مكتب صاحب النظام، لا مديرية فرعية.
- أي خطوة تحتاج موافقة (نفس `kernel.NEEDS_APPROVAL` الموحّدة) تتوقف
  وتُسجَّل بسجل الغرفة نفسها كرسالة ("يحتاج موافقتك: ...")، وتُحسم عبر
  `/api/room/confirm` بالضبط مثل `/api/confirm` العادي — بوابة موافقة
  واحدة، لا بوابة ثانية لكل قسم.

**العزل حقيقي لا شكلي**: كل غرفة ملف/مفتاح منفصل بالتخزين
(`rooms.history(room)` تفلتر بصرامة)، ورسالة بغرفة لا تظهر أبداً
بغرفة ثانية — فقط `recent_all()` (المراقبة) تتجاوز الفلترة عمداً.

**ما تم اختباره فعلياً هنا (9 اختبارات، سيرفر HTTP حقيقي):**
- 9 غرف تُسرَد صح (تنفيذية + 8 بوتات)، كلها فاضية قبل أي رسالة.
- رسالة محادثة عادية (بلا أدوات) بغرفة بوت — رد حقيقي محفوظ بنفس
  الغرفة، وغرفة ثانية مختلفة تماماً لا تتأثر إطلاقاً (تحققت صراحة).
- غرفة `executive` تشتغل بمسار عام منفصل عن أي بوت محدّد.
- رسالة تحتاج موافقة (`write_file`) بغرفة بوت توثيق — توقفت فعلاً،
  طلب الموافقة انحفظ كرسالة بنفس سجل الغرفة. موافقة عبر
  `/api/room/confirm` → **كُتب الملف فعلياً على القرص** (تحققت من
  القرص نفسه لا من رد الـAPI)، والحصيلة انحفظت بسجل الغرفة.
- غرفة غير موجودة → رفض 404/خطأ واضح من كل المسارات (الإرسال، القراءة).
- `/api/rooms/monitor` رأت فعلاً رسائل من 3 غرف مختلفة زُرعت بترتيبها
  الزمني الصحيح — لا فلترة خاطئة ولا خلط.
- `/api/rooms` (لمحة السايدبار) عرضت آخر رسالة حقيقية لكل غرفة، لا
  نصاً عاماً أو فارغاً كاذباً.
- فوق هذا: زرعت محادثات واقعية بـ5 غرف مختلفة، فتحت `/rooms` بمتصفح
  Chromium حقيقي عبر Playwright، أخذت screenshot لعرض "مراقبة — كل
  الأقسام" (كل الرسائل مجتمعة ومرتبة زمنياً، بادج ملوّن لكل قسم) وscreenshot
  ثانٍ لغرفة قسم محدّد بعد نقر فعلي على عنصر الواجهة — راجعتهما
  بصرياً، العرض صحيح ومقروء.

**ما يحتاج تجربتك على جهازك الحقيقي:** كل الاختبار أعلاه بمخ محاكى
(لا مفتاح API هنا) — أول محادثة حقيقية بغرفة فعلية هي أول اختبار لها
برد مخ حقيقي.

## خريطة الهيكل الكامل — إيش تم وإيش باقي

بنيت هذا على مراحل، كل مرحلة تُختبر حياً قبل الانتقال للتالية — بناء
50+ وحدة دفعة واحدة بلا اختبار هو بالضبط "كله عيوب" اللي حذّرتني منه.

**تم — كل أقسام الهيكل الثمانية اللي أرسلتها لها تطبيق حقيقي ومختبر:**
1. Owner Authority + Supreme Orchestrator + Executive/Strategic/
   Authority/Mission Control — `roles.py` + `router.py`
2. Independent Decision Council كاملاً (CDO, CRO, CVO, CSO, Chief
   Ethics, Independent Reviewer) — `roles.py`
3. ADJUDICATION & DECISION SYSTEM كاملاً **بما فيها Conflict/Deadlock
   Resolution** — `decision.py` + `chatroom.resolve()`
4. شبكة القيادة تحت مستوى القرار (8 مديريات، Mission Control) —
   `bots.py` (بوت واحد لكل مديرية؛ Domain Chiefs → Specialist Leads
   مؤجَّل عمداً، التفصيل أدناه)
5. طبقة التعلّم والتطور (Skill Registry، Regression Testing، Rollback،
   Sandboxed Experimentation، Self-Evolution Governance) — `skills.py`
   + `self_improve.restore()`
6. طبقة الأدلة والجودة (Claim Verification، False Success Detector،
   Decision Review & Audit) — `evidence.py`
7. طبقة التنفيذ والأدوات (Universal Tool Gateway، Browser Control) —
   توسيع `tools.py` (Secrets Vault مرفوض عمداً، التفصيل أعلاه)
8. مؤشرات القياس — `metrics.py`

**باقي عمداً، بأسباب واضحة لا كسل:**
- **Domain Chiefs → Specialist Leads** (أكثر من بوت واحد لكل مديرية):
  الآلية جاهزة بالكامل (`bots.py` سطر بيانات = بوت جديد). ما أضفت
  تخصصات وهمية بدون حاجة فعلية — هذا بالضبط "التعقيد اللي ما نبيه".
  تُضاف بوتات متخصصة إضافية لما يكون فيه مهمة حقيقية تحتاجها.
- **Capability Discovery التلقائي**: يحتاج منطق اكتشاف أنماط من
  السجلات لم أبنِه — بدل ادّعاء "اكتشاف تلقائي" وهمي.
- **Model Evaluation بالقياس الفعلي**: يحتاج مفاتيح حقيقية لأكثر من
  مزود مخ لأقيس أداءها وتكلفتها بصدق، لا افتراضاً.
- **Source Reliability + Uncertainty Estimator + Incident Learning**
  (بقية طبقة الأدلة) — امتداد مباشر لـ`evidence.py`/`memory.py`
  الموجودين، يُضاف بسهولة لما يظهر احتياج فعلي له.
- **API & Integration Gateway + Simulation/Digital Twin Engine**: لا
  حاجة خارجية محددة فعلياً الآن — بناء بدون حاجة ملموسة تخمين، لا هندسة.
- ~~Durable Workflow Engine~~ **مكتمل فعلياً** — `kernel.py` صار قابلاً
  للإيقاف والاستئناف حقيقة (`interactive=False` + `resume_task()`)،
  مبني لأن `web_chat.py` احتاجه فعلياً (راجع قسم "الشات عبر Daytona"
